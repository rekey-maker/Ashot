# 功能设计 v0.4.0 —— 裁切 / 缩放 / JPEG 交付（补齐 imgtool 的缺口）

> 日期：2026-10-29　版本：v0.4.0　基线：v0.3.0（commit `387db01`）
> 缘起：`图片标注工具/`（Pillow 版小工具）的三篇文档 + 六张示例图审查
> 结论——Ashot 的「看 / 标 / 屏幕区域截」之外，真正缺的是
> **对已有图片裁切、放大缩小、压成 JPEG**。本文写增量：契约、实现、
> 与 imgtool 的取舍、测试与真机证据。

---

## 0. 一句话

给 Ashot 补三个**图像几何**能力（裁切 / 缩放 / JPEG 编码），引擎复用
已有的「系统 .NET System.Drawing」路线（与矢量渲染同款），**不引入
Pillow**、不新增第二套标注实现；并用 `compose` 把「截屏→裁→缩→标→
存盘」压成一条命令。

## 1. 为什么不是把 imgtool 搬进来

imgtool（`图片标注工具/imgtool.py`，300 行 Pillow）证明了三件事该做，
但它自己的实现有 5 处硬伤（2026-10-29 实跑复核，见 §6）。如果照搬，
等于把「两套箭头几何、两套坐标语义、两套收据哲学」一起搬进零依赖仓库。

**取舍表（继承什么 / 不继承什么）**：

| imgtool 的 | 处置 | 理由 |
|---|---|---|
| `crop` 裁切 + `--scale` 放大 | ✅ 继承（`ashot crop`） | 真缺口；ashot_shot 的 area 只能**截屏时**限定屏幕区域 |
| `resize` 缩放 | ✅ 继承（`ashot resize`，含 `--max-side` 只缩不放） | 发图/进上下文都要控体积 |
| `--jpg Q` / `--max-side` | ✅ 继承，并扩到 `annotate` 与 `compose` | 2.3MB PNG 发出去不现实 |
| `compose` 一条命令 | ✅ 继承（CLI） | 步骤多、坐标容易错，文档里它是「高价值第 1 条」 |
| `--from-css --dpr` | ✅ 收窄成 `crop --dpr K`（box 是 CSS 就乘） | 语义单一，只在裁切处需要 |
| `--box x1,y1,x2,y2` | ❌ 改为 **x,y,w,h** | 与 `shot --area l,t,w,h`、ops 的 rect 统一；**收据回显 crop 与 crop_px，写反一眼可见** |
| `--text x,y` + 共用 `--label` | ❌ 改为 `--text "x,y:文字"` | 旧行为：多个 `--text` 输出同一句（实测），文档写「可多次」但做不到 |
| PIL 抗锯齿 | ❌ 用 GDI+ | PIL ImageDraw 硬边（3× 放大实测台阶）；ashot 的矢量路早就因「箭头有马赛克感」换掉了 |
| 越界静默裁切 | ❌ 改为 `bounds_warn` + 夹到边界 | 示例图 `示例-css坐标.jpg` 的右边框消失就是静默裁切的产物 |
| 收据 = Python dict repr | ❌ 统一 JSON | `{'ok': True}` 不是合法 JSON，脚本消费要额外处理 |

## 2. 范围

**做**：
1. `ashot/transform.py`：`crop` / `resize` / `jpeg` 一条流水线（`apply()`），
   另出 `png_size` / `normalize_crop` / `plan_size` / `default_out` 纯函数。
2. `ashot/_gdi_image.ps1`：GDI+ 忠实执行（裁 → 双三次缩放 → 编码），
   纯 ASCII 纪律（同 `_gdi_render.ps1` 的教训）。
3. CLI：`crop` / `resize` / `compose`；`annotate` 增加 `--jpg/--quality/
   --max-side`。
4. MCP：`ashot_crop` / `ashot_resize`（22 工具）；`ashot_annotate`
   增加 `jpg/quality/max_side`。
5. **截图即缩放**：`shot --scale/--max-side/--jpg` 与 MCP
   `ashot_shot(scale,max_side,jpg,quality)`——截完不必再跑一次
   `resize`（`output.save` 增加 `ext`，否则 `--jpg` 会落进 `.png` 壳）。
6. `ashot/output.py`：`image_size()`（PNG IHDR + JPEG SOF 嗅探），
   `preview_jpeg` 改用它——否则 JPEG 输出进不了缩图梯次。

**不做**：PIL/Pillow；批量目录处理（imgtool 建议 5，仍待做）；打码
（ashot 已有 mosaic/blur，不必重复）；Mac 的 sips 分流（v0.2.0 批2）。

## 3. 契约

### 3.1 坐标系（最容易错的地方）

- `box` = **源图像素**的 `x,y,w,h`（左上角 + 宽高），**不是** x1,y1,x2,y2；
- `dpr>0` 表示 box 给的是 CSS 像素（DevTools 的 getBoundingClientRect），
  内部先乘 dpr 再裁——省手算，也避免「CSS 当像素」的静默错位；
- **先裁后缩**：缩放作用在裁切后的尺寸上，`ops` 坐标因此按「裁缩后的
  图」给（`compose` 的 stderr 与 MCP 收据都会写明 `coord_space`）；
- 收据同时回显 `crop`(x,y,w,h) 与 `crop_px`(x0,y0,x1,y1)——box 写反时
  数值自曝，不用猜。

### 3.2 越界

| 情形 | 行为 |
|---|---|
| 部分越界 | **夹到图边** + `bounds_warn`（"crop 右边界越界 256 px（已夹到图宽 2544）"） |
| 完全在图外 / 宽高 ≤0 | 报错（ValueError/异常收据），不返回空图 |
| 缩放参数同给多个 | 报错（"缩了再缩"没有唯一解，猜一个不如让人写清） |
| `max_side` 小于原图 | 才缩；**不放大**（与 preview 同语义） |

**告警优于裁切**（v0.2.6 Q15 的同一条哲学）：宁可多说一句，也不静默
丢内容——imgtool 的示例图就是反例。

### 3.3 引擎与降级

引擎**只有** GDI+（`System.Drawing`）。失败时**不**降级到「纯 Python
慢速兜底」：那条路解码一张 2544×1632 PNG 就要 1.58s、再编码 1.76s
（本机实测），静默换上去等于把「快」变成「不可用」。所以失败就带原因
报错（`ps_rc=...: <stderr>`），与矢量标注的降级策略不同——因为那边
**有**等价的像素画布，这边没有。

引擎能力：
- 缩放 = `HighQualityBicubic` + `PixelOffsetMode.HighQuality`；
- JPEG 输出强制 24bpp（JPEG 无 alpha，不让编码器猜）；
- PNG 输出 32bpp（保留截图的透明通道）；
- 无裁无缩且要 PNG = **原样返回**（`engine: "passthrough"`，像素零损失）。

### 3.4 收据字段

```json
{"ok": true, "path": "...", "src": [2544, 1632], "w": 833, "h": 1764,
 "crop": [1850, 90, 694, 1470], "crop_px": [1850, 90, 2544, 1560],
 "scale": 1.2, "format": "jpeg", "quality": 85, "bytes": 131081,
 "coord_space": "src_px", "engine": "gdi+", "ms": 418,
 "bounds_warn": ["..."]}            // 有越界才出现
```

`ver`（进程版本）仍由 `_serve` 单一出口盖章。

## 4. 实现

```
PNG/JPEG?（只吃 PNG 源）
   │
   ├─ normalize_crop(box, dpr) ── 夹取 + 告警（纯函数，可单测）
   ├─ plan_size(w,h,scale|width|max_side) ── 互斥校验（纯函数）
   ▼
_gdi_image.ps1（spec JSON: in/out/crop/size/format/quality）
   ├─ Bitmap.Clone(rect) 裁
   ├─ 新建 Bitmap(24bpp|32bpp) + Graphics 双三次 DrawImage 缩
   ├─ PNG: ImageFormat.Png / JPEG: Encoder Quality
   └─ 末行 JSON {"ok":true,"w":..,"h":..,"bytes":..}
   ▼
transform.apply() -> (bytes, info)；ps 报的尺寸与 Python 算术不一致时
写 size_mismatch（不让 Python 替引擎背锅）
```

**为什么 PS 而不是纯 Python**：实测同一张 2544×1632 图，纯 Python
解码 1.58s + 编码 1.76s；GDI+ 全流程 0.35~0.45s，且抗锯齿/双三次质量
本来就要靠系统引擎。零依赖红线不破（.NET 是系统自带，与 GDI+ 渲染同
一条既有路线）。

**一个坑（写进脚本注释）**：spec 里的路径可能含中文。Python 侧
`json.dump(..., ensure_ascii=True)` 把非 ASCII 转 `\uXXXX`，PS 侧
`ConvertFrom-Json` 还原——绕开「PS 5.1 按 ANSI/GBK 读文件」的旧伤。

## 5. 测试与真机

**自动化**（`tests/test_transform.py`，30 项）：plan_size 规则/互斥、
裁切后逐像素证明裁的是哪一半、越界告警文案、完全图外报错、dpr 换算、
先裁后缩顺序、放大与缩小、passthrough、JPEG 魔数/尺寸/体积、`.jpg`
扩展名推导、缺省命名（父目录带点）、CLI crop/resize/annotate --jpg/
compose、MCP 收据与越界告警。全套 **141 项**通过。

**真机**（本机 3840×2160 桌面，2026-10-29）：

| 操作 | 结果 |
|---|---|
| `shot` 全桌面 | 3840×2160 PNG |
| `crop --box 350,420,600,700` | 600×700，345ms，文件树文字清晰无糊 |
| `crop --box 970,330,1100,900 --scale 1.5` | 1650×1350，435ms，代码 1.5× 放大后字形平滑（双三次） |
| `resize --max-side 1400 --jpg 85` | 1400×898 / 228KB（原 2.28MB） |
| `shot --max-side 1600 --jpg 85` | 1600×900 / 206KB / 424ms（4K 全桌面截完直接压，不必再跑 resize） |
| `compose`（裁 980×950 + 框/箭头/中文） | 980×950 JPEG 126KB，1046ms，抗锯齿边缘 + 中文正常 |
| MCP 协议冒烟（initialize/list/call） | 22 工具、`ashot_crop`/`ashot_resize` 可调、ver=0.4.0 |

## 6. 审查证据（imgtool，2026-10-29 实跑）

| 现象 | 证据 |
|---|---|
| `--area` 文档写 `l,t,w,h`，实际是 `l,t,r,b` | `ImageGrab.grab(bbox=(0,0,100,60)).size == (100,60)`；代码把 `parse_box` 直接喂 bbox，所以 `--area 600,300,1600,1100` 实际截 1000×800 |
| 越界静默 | `--rect 2400,1500,400,300`（图宽 2544）→ `ok:true, marks:1`，无告警 |
| 多个 `--text` 共用一条 label | 实跑两处 `--text` → 两处都渲染同一句 |
| 箭头头长 8×width、无短箭保护 | 100px 箭 + width=6 → 头占全长约 42% |
| 无抗锯齿 | 3× 放大可见台阶 |

这些坑**没有**复制进 Ashot：坐标语义统一、越界必告警、文字按处、
箭头复用 v0.1.8 的几何、渲染走 GDI+ AA。

## 7. 边界与后续

- **Windows only**：裁切/缩放/JPEG 依赖 .NET；Mac 走 v0.2.0 批2 的
  `sips` 分流（设计已列，未开工）。CDP 能力仍跨平台。
- **只吃 PNG 源**：`png_size` 对 JPEG 源报「不是合法的 PNG」——imgtool
  能吃任意格式，Ashot 暂不扩（截图/标注产物都是 PNG）。
- **批量目录**（imgtool 建议 5）未做：价值在「教程批量出图」，等真需求。
- 大图内存：GDI+ 一张 4K 图约 33MB，拼接/批处理时才需要担心。

## 8. 审查结论（子 agent 只读审查，2026-10-29）

**结论：P0×1 / P1×4 / P2× 若干；P0+P1 全部修完，P2 采纳 5 条。**

| 级别 | 发现 | 处置 |
|---|---|---|
| P0 | `apply()` 先用 `mkstemp` 占了输出路径，「PS 没写出文件」判据**恒为真**——PS 静默失败会交付 0 字节文件（实测返回 `b''` 且 `engine=gdi+`） | 改为占位后 `unlink`，再加「非空 + 魔数（`\x89PNG` / `\xff\xd8`）匹配」双校验，不符即 `RuntimeError` |
| P1 | 引擎上报尺寸缺失时整段短路不核对；只有 w 无 h 还会 `TypeError` | 缺 w/h 或与请求不符 → 直接 `RuntimeError`（不让 Python 算术替引擎背锅） |
| P1 | 只认 PNG 源，JPEG 再裁一刀报「不是合法的 PNG 字节」 | 改用 `output.image_size`，**PNG/JPEG 都收**（GDI+ 本来就能读） |
| P1 | `ashot_shot` 的 docstring 被误写入 annotate 的 v0.4.0 段落（模型会按描述传不存在的参数 → TypeError） | 删掉，段落只留在 `ashot_annotate` |
| P1 | CLI `annotate`/`shot` 把 informational 行打到 stdout，破坏「stdout 只留路径」 | 两处改走 stderr |
| P2 | `dpr` 无 crop 静默忽略 / 银行家舍入 / `out_path` 尾分隔符产出 `dir/.jpg` / `_parse_box` JSON 分支不校验 / conftest 污染工作树 | 前四条已修；conftest 保留 repo 内 `tmp/pytest` 并注明「本机 `mkdtemp`+`chmod` 实测不可用」——不是偏好，是沙箱边界 |

**不采纳**：`_gdi_image.ps1` 异常路径 try/finally（每次调用新起进程，
收益低于改坏脚本的风险，已记录）；`_jpeg_size` 的 EXIF 方向（只喂自家输出）。

**复核后不成立的一条**：审查说「x<0 时越界文案数值算错（报 50 实际夹掉
60）」——逐边报数是对的：左 10 + 右 50 = 60，`右边界越界 50 px` 无误。

审查方未跑 pytest（静态走查）；修复后本地全套 **139 项**通过，且真机
（4K 桌面）复跑三例（裁 1:1 / 1.5× 放大 JPEG / compose 标注）输出与
修复前逐字节一致。
