## 0. 一句话

仓库根新增独立小工具 `shot.py`（约 80 行，零第三方依赖）：桌面/窗口/
框选截图存 PNG。**纯系统调用，daemon 不在线照常可用**——定位是
「ALrec 收养的工具，不是 ALrec 的器官」：代码住 ALrec 仓库、输出默认
进 ALrec 数据区，但不 import ALrec 任何代码、不连 8765、可被任意项目
直接拿走用。

## 1. 需求与动机

- agent（本工具的主要用户）此前「桌面盲」：看网页靠无头浏览器、看直播
  靠 snap 抽帧，但看用户桌面/原生窗口只能求用户手截。2026-10-27 实测
  PowerShell .NET 路线打通后，该能力可以产品化（固定入口、稳定行为、
  不靠 agent 现编脚本）。
- 用户侧顺手价值：双击 bat 即截屏（比 Win+Shift+S 多了「自动落盘+
  时间戳命名」），可作为快速留存屏幕信息的习惯入口。

## 2. 硬性约束（用户定案 + 实测在案）

1. **不依赖 daemon**：纯 GDI 系统调用（ctypes/PowerShell 双实现），
   不 import ALrec 代码、不连 8765；
2. **高 DPI**：进程内 `SetProcessDPIAware` 必须在截屏前调用——否则
   缩放 125%/150% 的机器截出拉伸糊图（Win11 默认缩放常触发）；
3. **多显示器**：默认全虚拟桌面（`VirtualScreen`），`--screen N` 选
   单屏（枚举 `Screen.AllScreens`）；
4. **输出落点**：默认 `~\Ashot\shots\<时间戳>.png`
   （用户数据区，不进仓库不进桌面——2026-10-25 Downloads 卫生纪律
   同款思路）；`--out <路径>` 覆盖；目录不存在自动建；
5. **绝不进仓库截图**、绝不静默上传（本工具无网络面）。

## 3. 功能面（首版四动作）

| 命令 | 行为 | 备注 |
|---|---|---|
| `python shot.py` | 全虚拟桌面截屏 | 缺省动作 |
| `python shot.py --screen N` | 第 N 块物理屏 | `--list-screens` 列屏 |
| `python shot.py --win` | 前台窗口 | GetForegroundWindow → GetWindowRect |
| `python shot.py --area L,T,W,H` | 指定区域 | 像素坐标 |

通用参数：`--out <路径>`（文件或目录）、`--open`（截完用系统默认看图
器打开）。失败一律非零退出码 + stderr 明文（零静默）。

## 4. 实现要点（两条腿，ctypes 优先）

- **主实现 ctypes**：`user32.SetProcessDPIAware` → `GetDC/BitBlt` →
  `GDI+` 存 PNG。优点：单进程完成、无窗口闪烁；缺点：GDI+ PNG 编码
  的 ctypes 声明较长（~40 行样板）。
- **兜底实现 PowerShell**：`System.Windows.Forms.Screen` +
  `CopyFromScreen` + `Bitmap.Save`（2026-10-27 实弹已验证，1920×1080
  通）。ctypes 路径任何一步失败时自动降级此路，仍失败才报错。
- 已知边界（照抄 DSH 实弹经验）：远程会话/服务态可能截出黑图——工具
  应检测全黑帧并提示「当前会话可能无交互桌面」。

## 5. 独立 MCP（ashot 域名，v0.1.0 即含）

stdio JSON-RPC 手写（alrec_mcp 同款零依赖范式），注册宿主 mcp.servers.ashot：

| 工具 | 参数 | 行为 |
|---|---|---|
| `ashot_shot` | mode(full/screen/win/area), screen?, out?, clip?, keep? | 截图（v0.1.0 即注册） |
| `ashot_annotate` | image, ops(JSON 数组) | 事后代码标注（v0.1.1 预留，随标注模块） |

agent 场景=主要用户：截图后拿绝对路径喂读图，或 --clip 进剪贴板零留痕。

## 6. 模块化结构（用户定案：标注归标注、截图归截图，各 py 文件）

```
Ashot/
├── ashot/
│   ├── __init__.py      # __version__（烙印对：与 mcp.py 声明同步）
│   ├── capture.py       # 截图：GDI/PowerShell 双腿、DPI、多屏、四动作
│   ├── annotate.py      # 标注：七件绘制原语 + B 交互窗(ttk)/C 命令行双形态
│   ├── output.py        # 交付：落盘命名/剪贴板(--clip)/retention 清理
│   ├── mcp.py           # stdio MCP 脸（零业务，转发上面三模块）
│   └── cli.py           # 命令行入口（argparse：shot/annotate 两子命令）
├── SKILL.md
├── alrec 收养期文档      # docs/design/（沿革存档）
└── tests/
```

模块纪律：**capture 不 import annotate，annotate 不 import capture**（单向
依赖只在 output/cli 汇聚）——截图能单独用，标注能对任意既有图片用。

## 7. ALrec 侧关系（已解耦）

ALrec 零改动：其待商榷文档标注「方案迁移至 Ashot」；SKILL/MCP 不含截图条目。
两仓库完全独立演进，无共享代码。

## 7.5 ShareX 源码拆解对照（2026-10-27，用户提供了官方源码包）

用户下载了 ShareX-develop.zip（C# 官方源码）供拆解。项目切分极其清晰，
对我们三个直接参照物：

| ShareX 模块 | 内容 | 对 Ashot 的启示 |
|---|---|---|
| ScreenCaptureLib（仅 9 文件） | 捕获核心极小：Screenshot.cs 168 行（CaptureRectangle/Fullscreen/Window/ActiveWindow/Monitor 五入口）+ 区域交互 + 滚动截屏 383 行 | **印证我们「捕获核心很小」的判断**；五入口与 Ashot 四动作几乎一一对应；滚动截屏独立成文件（383 行）印证「重活独立挂账」裁决 |
| ImageEditor/Core/Annotations（31 个形状类） | 标注全集：Rectangle/Ellipse/Arrow/Line/Text/Freehand/Crop/Cursor/Emoji/Number/Step/SpeechBalloon + Effects 组（Blur/Pixelate/Highlight/Magnify/Spotlight）+ SmartEraser | 我们七件=其高频子集；**值得抄的新种**：StepAnnotation（步骤编号 ①②③，教程场景神器）、Spotlight（聚光灯压暗四周）、NumberAnnotation（自动编号）——记入 v0.2 候选；SmartEraser（智能擦除=用背景色块覆盖）实现极简也可抄 |
| HistoryLib | 任务历史独立成库 | 印证「历史管理独立演进」；Ashot 首版用 retention 目录收敛替代，形态一致 |
| ImageEffectsLib | 效果管线（水印/边框等预设） | Ashot 不做（效果≠标注），无启示 |
| ScreenRecordingLib | 录屏 | 已独立挂账 ALrec 待商榷（ddagrab 路线），不抄——C# WPF 全套 vs 我们 ffmpeg ddagrab 一条命令 |

**v0.1.1 增补裁决（用户批）**：四件新标注种直接做进 annotate.py——
Step（步骤编号，自动递增 ①②③）/ Number（显式编号）/ Spotlight（聚光灯：
目标区域保持原样、四周压暗 50% 黑）/ SmartEraser（智能擦除：目标区域
用四角均值色实心填充——比马赛克「擦得干净」）。ops kind：`step`（自动
编号，同一次 ops 内递增）、`number`（带 value）、`spotlight`（x,y,w,h
[dim=0.5]）、`smarterase`（x,y,w,h）。原语全在像素画布层实现（步数编号
复用 text/点阵、聚光灯=全图乘暗系数+目标区回贴、智能擦除=均值填充）。

实现层注意：ShareX 是 C#/WPF（GPU 加速 UI），Ashot 是 Python 标准库——
**抄架构与功能清单，不抄实现**；其 31 类标注的「类别学」（Base→Point 标/
Effect 标/自由绘）可借来规整我们 annotate.py 的 ops schema（kind 已按此
分组：形状类 vs 效果类 mosaic/blur）。

- 不做标注/贴图/托盘（那 SnippingTool 的活）；
- 不做连续截屏/录屏（ALrec 主业已有）；
- 不做网络上传（隐私即卖点）；
- 不做窗口枚举选择列表（首版只「前台窗口」，够用再说）。

## 7.6 矢量标注设计（2026-10-28，v0.1.6/v0.1.7 增补）

### 7.6.1 背景与两次用户裁决

1. **v0.1.6**：用户实战验收时反馈「箭头样式有点丑，边缘有马赛克一样的
   感觉」——纯像素画布（Bresenham 加粗 + 硬边多边形填充）没有抗锯齿，
   这是硬边像素判定的天性，调参数救不了。同轮用户贴微信截图问
   「箭头能做这种吗」→ 拍板**渐变实心箭头**（「当然要效果最好的」）。
2. **v0.1.7**：追问「不能画矢量图？合并进去」→ 矢量渲染整体合并。

### 7.6.2 方案选型（三条路）

| 路线 | 结论 |
|---|---|
| 纯 Python 抗锯齿（超采样/解析覆盖率） | 工程量大（每种原语一套覆盖率积分），性能差，放弃 |
| SVG 输出/外部光栅化器 | 零依赖红线内没有 SVG 光栅化器，且标注必须合并进截图（光栅合成不可绕），放弃 |
| **GDI+ System.Drawing**（微信截图同款引擎） | **胜出**：.NET 系统自带=零第三方依赖红线不破；SmoothingMode.AntiAlias 真矢量；DrawString 附带解决中文文字 |

### 7.6.3 双后端架构（几何与渲染分离）

```
JSON ops ──> vector.py（几何编译器：纯数学，可单测）
                │  矢量形状 → 指令 JSON（stroke 路径点列 / fill 多边形 / text / dot）
                │  像素操作 → 原样分流
                ▼
        _gdi_render.ps1（GDI+ 忠实执行：DrawLines/FillPolygon/
                DrawString/FillEllipse，SmoothingMode=AntiAlias）
                ▼
        有像素 ops？→ annotate.py 像素画布叠加（mosaic/blur/spotlight/smarterase）
                ▼
        PS 任一环节失败 → 整单降级纯像素画布 annotate_png
```

**形状分流表**（谁走矢量、谁留像素）：

| 类别 | 原语 | 后端 | 理由 |
|---|---|---|---|
| 矢量形状 | rect/ellipse/line/arrow/step/number/text | GDI+ | 有「边缘」，抗锯齿有意义 |
| 像素操作 | mosaic/blur/spotlight/smarterase | 纯像素画布 | 邻域统计操作，无边缘概念，AA 无意义 |

**收据契约**：`backend` 字段如实标注 `gdi+`（矢量）或 `pixel`（降级/
纯像素 ops）——agent 一眼知道走的哪条路，绝不假装。

### 7.6.4 几何规格要点

- **stroke** = 密集路径点列 + GDI+ Pen（`RoundCap`/`RoundJoin`）：
  圆角 rect=四直段+四角各 16 段 90° 弧；ellipse=96 段参数方程；line=两点。
- **fat arrow（渐变实心箭头）fill 多边形**：渐变杆左右轮廓（半径
  r_tail→r_head 幂 0.6 快速增粗——线性渐变尾巴呈针状，实测难看）+ 实心
  三角头（head_len=max(12,width*5)，半底宽 0.72×head_len）+ 圆尾 12 段弧
  闭合；`width` 语义=头部粗细基准；`style:"line"` 回退旧直杆。
- **dot（step/number）**：FillEllipse 圆底 + MeasureString 居中数字
  （Bold，1.15×半径字号）。
- **text**：DrawString 微软雅黑 Bold，Font 以 `GraphicsUnit.Pixel` 构造
  （字号确定性，不受宿主 DPI 影响）→ **中文可标注**，解除 8x16 点阵
  仅 ASCII 限制。
- 坐标全部 Python 侧 float 计算后 round(2) 序列化，PS 零形状数学
  （只忠实执行——几何可测，渲染 dumb）。

### 7.6.5 实锤坑（进 SKILL/注释的红线）

**PowerShell 5.1 读无 BOM `.ps1` 按 ANSI/GBK 解码**：UTF-8 中文注释的字
节错位吞掉行尾、把 `param($SpecPath)` 行并进注释（参数全空、矢量路静默
降级、三个端到端测试全 backend=pixel 才暴露）。→ `_gdi_render.ps1` **纯
ASCII 纪律**（注释英文），文件头已声明缘由。

### 7.6.6 测试锁（v0.1.7 全套 40 项中矢量相关）

- 几何编译单测：fat arrow 多边形闭合/点数、未知 kind/坏 hex 抛错、
  像素 ops 分流
- **AA 中间色分水岭**：描边边缘必须存在红底混合过渡像素（纯像素画布为
  0——这是两种后端的可判别差异，防「静默降级却以为在用矢量」）
- 混合 ops：backend=pixel 且像素操作在矢量输出上真实生效
- 中文文字：DrawString 产出非底色笔画（占位框时代的回归不再可能）

### 7.6.7 版本与发布形态

v0.1.6（渐变箭头+圆角）与 v0.1.7（矢量后端）各自独立 commit/tag/release；
CHANGELOG.md 承载全版本史；对外发布说明以 GitHub Release notes 为准。

## 7. 业界能力面对照（2026-10-27 调研：ShareX/Snipping Tool/Flameshot）

成熟截图工具的通行运行流程是五段：**捕获 → 暂存 → 编辑 → 交付（存盘/
剪贴板/上传）→ 历史管理**。对照我们首版的覆盖度与裁决：

| 业界能力 | ShareX/Snip | 我们首版 | 裁决 |
|---|---|---|---|
| 捕获（全屏/区域/窗口/滚动） | ✅ | 全屏/区域/前台窗（无滚动） | 够用；滚动截屏不做（长图拼接是重活） |
| **暂存（临时文件生命周期）** | 自动清理临时目录 | ❌ 未设计 | **本节补上，见下** |
| 编辑（标注/裁剪/马赛克） | ✅ | ❌ | 不做（SnippingTool 的活，边界即设计） |
| 交付：剪贴板 | ✅ | ❌ | **首版补**：截图后默认同时进剪贴板（agent 零文件路径直接 Ctrl+V 场景高频） |
| 交付：上传 | ✅ | ❌ | 永不做（隐私即卖点不变） |
| **历史管理** | 任务历史窗 | ❌ | 首版不做历史窗，但**目录收敛策略**要做（见下） |

### 7.1 临时文件生命周期（用户点名的重点）

业界通行做法是**双目录分层**：临时产物（未确认的捕获、编辑中间态）进
系统临时目录由「退出清理/定期清理」管；用户确认的成品才落正式目录。
ShareX 更进一步用「任务历史」+可配置的自动清旧。

shot.py 的对应设计（单发进程形态下最简且够用）：

1. **没有编辑态=没有真正意义的临时文件**——首版截完即写正式目录，
   一步到位，天生不产生「未确认暂存」；
2. **正式目录的收敛策略**（防 shots/ 重蹈 tmp/ 积压覆辙）：
   `--retention-days N`（缺省 **30 天**），每次运行顺手清理超过 N 天的
   旧截图——单发工具的「定期清理」就搭在自身运行的便车上，无需常驻；
3. `--keep` 跳过本次清理（用户想囤时用）；
4. 清理动作落一行 stdout（清了几张/释放多少），不静默。

### 7.2 附加小能力（对照后值得抄的）

- **`--clip` 显式只进剪贴板不落盘**（临时场景：发给 AI 看，完事不留痕
  ——隐私友好的「阅后即焚」路径）；
- `--open` 已在首版（截完即看）。
