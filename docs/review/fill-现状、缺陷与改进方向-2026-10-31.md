# fill 能力审查与改进分析（v0.7.4）

> 日期：2026-10-31　分支：`feat/v0.7.4-fill`（HEAD `7dde955`）
> 基线：`main` / `v0.7.3`（`c145464`）　测试：**205 passed, 6 skipped**
> 性质：只读分析 + 子代理复核台账；**本文不包含代码改动**。
> 范围：只讨论 `fill`（色块填充）及其直接相关的层序/图层问题，不展开渐变、滤镜等。

## 0. 一页结论

1. **fill 能用，但交付链没闭环**：不写 `color` 会带默认红边；半透明 fill 无法配同 alpha 描边；
   preview/JPEG 会把透明底压成近乎不透明。
2. **没有图层**：只有 ops 数组的隐式画家顺序；没有 `layer`/`z`/`visible`/组透明度。
3. **两个后端的像素 ops 层序相反**：GDI+ 恒最后，像素降级路按数组顺序——图层排序的地基不统一。
4. **孔洞不是完全做不到**：单条 polyline 的“反向内环 + 双走缝线”可出洞；缺的是**多子路径/干净孔洞**。
5. **fill 只解决了“上色”**，还没解决“脸挖眼睛、甜甜圈、月牙、彩虹拱”这类复合形状；arc 只有扇形，没有 chord。
6. **测试有假绿**：现有“凹多边形”用例不自交，nonzero/evenodd 同结果；真正能判别 Winding 的五角星没测。

### 优先级

| 级别 | 事项 | 理由 |
|---|---|---|
| P1 | `stroke:false`（或明确定义的不描边） | 半透明 fill 目前**没有**无边框替代；`width=0` 是硬报错 |
| P1 | preview/JPEG 的 alpha 处理与收据 | 用户/模型看到的图与实际 PNG 不一致 |
| P1 | 多子路径 / `holes` / arc `chord` | 人脸、甜甜圈、月牙、彩虹拱 |
| P1 | 统一两后端像素 ops 层序 | 图层排序的前置条件 |
| P2 | 轻图层 `layer:int` + visible | 重排/隐藏；不做组透明度 |
| P2 | 真图层（组透明度/混合） | 需逐层离屏合成，成本最高 |
| P2 | 像素抗锯齿、radius 随 dpr、校验/告警收尾 | 观感与契约 |

## 1. 对外契约（当前）

| 项 | 现状 |
|---|---|
| 字段 | 每个 op 可选 `"fill": "#RRGGBB"` 或 `"#RRGGBBAA"`（alpha 在后） |
| 支持形状 | `rect`（含 `radius`）、`ellipse`、`curve`、`arc`、`polyline` |
| 不支持 | `line`、`text`、`arrow`、`step`、`number`、`mosaic/blur/spotlight/smarterase`；`apply_pad` 直接报错 |
| 顺序 | 同一 op 内 **先 fill 后 stroke**，描边压在色块上 |
| arc | fill = **扇形**：圆心 → 弧采样点 → 闭合回圆心；stroke 仍是弧线 |
| curve/polyline | fill 时自动闭合（末点连回首点）；stroke 不闭合 |
| 规则 | 固定 **non-zero / Winding**；GDI+ 显式 `FillMode.Winding`，像素路同规则 |
| 半透明 | **仅 fill 支持 8 位色**；`color`（描边/文字）只收 6 位，8 位入口报错 |
| 组合 | selector/ref 只支持**矩形族与 text**；fill 加在 `rect/ellipse` 上可用；`curve/arc/polyline` 不能 selector/ref |
| pad | 只对矩形族（rect/ellipse/mosaic/blur/spotlight/smarterase）生效；fill 跟随 |
| dpr | 坐标随全局 dpr 缩放；**radius 不缩放**（见 §4.7） |

## 2. 渲染管线

### 2.1 校验与编译

- `vector.apply_pad`：kind 是否支持 fill、fill 颜色长度、8 位 `color` 拒绝、未知字段；
- `vector.compile_ops`：rect/ellipse/curve/polyline/arc 生成 `fill` + `stroke` 两个 shape（共用 `i`）；
- `_fill`：点数 <3 报错；`_stroke`：再次拒绝 8 位 color；
- `annotate._color_a`：像素路 fill 颜色解析（第 5 处校验）。

### 2.2 矢量路（GDI+）

- `_gdi_render.ps1` 手动解析 `#RRGGBBAA`（`ColorTranslator` 的 8 位是 `#AARRGGBB`，会错位）；
- `FillPolygon(..., FillMode.Winding)`；
- 圆角矩形复用 `_rect_path`，椭圆复用 `_ellipse_path`，弧用“圆心 + 弧点”扇形；
- **像素 ops 恒在所有 shapes 之后执行**，与数组位置无关（既有契约）。

### 2.3 像素降级路

- `Canvas.fill_polygon`：扫描线 + 非零环绕；像素中心判定；
- alpha 按目标 alpha 做 source-over（透明底已修）；
- **无抗锯齿**，边缘硬；
- 像素 ops 按 ops 数组顺序执行，因此与 GDI+ 路的层序不同。

### 2.4 层序差异

| 输入 | GDI+ 路 | 像素降级路 |
|---|---|---|
| `[mosaic, fill]` vs `[fill, mosaic]` | 输出相同（fill 总被 mosaic 覆盖） | 输出不同（数组顺序决定谁盖谁） |
| `[spotlight, 红 fill]` | fill 被压暗 `(127,0,0)`（子代理实测） | fill 盖住 spotlight `(255,0,0)`（子代理实测） |
| 同一份 ops 降级 | 覆盖关系可能反转 | 覆盖关系可能反转 |

本窗口实测：`mosaic` + 红 fill 两种顺序，**GDI+ 哈希相同、像素路哈希不同**，确认层序不一致。

## 3. 已验证可用

- 五类闭合形状填色；arc 扇形；curve/polyline 自动闭合；
- 实心 fill 两路中心像素一致；半透明 fill 在 opaque / 全透明 / dst-alpha=128 三种底上两路 alpha 混合一致（子代理实测）；
- `pad=10`、`dpr=2` 填充跟随缩放（子代理实测）；
- `rect` w/h=0 两边都不填、负 w/h 两边都填、radius 超半短边两边都夹、sweep 0 报错、360/720 成整圆（子代理实测）；
- selector/ref 对 `rect/ellipse` 可用；对 `curve/arc/polyline` 明确报错；
- 五角星（点序 0,2,4,1,3）中心两路都出绿 `(0,255,0)`；`radius=20` 圆角外点两路都是背景、中心是填充色（本窗口复跑）；
- MCP `ashot_annotate` 的 fill 实测通（子代理实测，中心像素 = 填充色），缺回归测试；
- CLI `--ops-file` fill 端到端通；`bounds_warn` 仍亮。

## 4. 缺陷与缺口

### 4.1 fill 交付链不闭环（P1）

**默认红边**：不写 `color` 时仍画 `#FF3B30`、`width=3` 的描边。本窗口实测：

```json
{"kind":"ellipse","x":20,"y":20,"w":40,"h":30,"fill":"#20C060"}
```

在 (20,35) 两路都是 `(255,59,48,255)`——绿色块带红边。

**半透明 fill 无法无边**：

- `color` 只收 6 位，`fill:"#FF000080"` 配不出同 alpha 的描边；
- 同色 6 位描边仍不透明，且以路径为轴每边外扩 `width/2`；
- `width=0` 双路**硬报错**，不是“不描边”。

**preview/JPEG 丢 alpha**：透明底 60×60 + `#FF000080`：

| 输出 | 像素 |
|---|---|
| PNG | `(255,0,0,128)` |
| preview JPEG | `(254,0,0,255)`（本窗口实测） |
| `jpg=85` 落盘 JPEG | `(188,0,0,255)`（子代理实测） |
| 不透明底上 PNG/preview | `(144,16,16)`（正确） |

模型/用户看 preview 时看到的是近乎不透明的红，与 PNG 不符。

### 4.2 两后端像素 ops 层序相反（P1）

见 §2.4。SKILL/MCP 把“像素 ops 恒最后”写成全局契约，但只有 GDI+ 成立；降级路按数组顺序，同一份 ops 在降级后覆盖关系反转。

### 4.3 孔洞与复合路径（P1）

- **能**用单条 polyline 的“反向内环 + 双走缝线”在 nonzero 下出洞；本窗口实测洞心 `(32,32,32,255)`、体心 `(0,255,0,255)`，两路一致；
- **缺**多子路径声明：一个 op 只能一条点列，无法做“无缝线、能单独描边的干净孔洞”；
- 场景：人脸挖眼睛、甜甜圈/轮胎、字母 O、月牙、彩虹拱；
- arc 只有扇形，没有 chord（弦切）/segment（弓形）。

### 4.4 没有图层（P2，用户明确提出）

现状：

- z 序 = ops 数组顺序；fill 能压住文字/形状；
- 像素 ops 恒最后（GDI+）；
- 无 `layer`/`group`/`z`/`visible`/`opacity` 字段——`layer` 进 `apply_pad` 直接“未知字段”拒绝（本窗口实测）；
- 无组隔离：两个 50% 红 fill 重叠（白底），本窗口实测单区 `(255,127,127)`、重叠区 `(255,63,63)`——二次混合，组透明度无法靠 per-op alpha 冒充。

### 4.5 点数校验不对称（P2）

- `_fill` 的 <3 点校验只在矢量路；
- 像素路 `fill_polygon` 对 n<3 直接 `return`；
- 本窗口实测 2 点 polyline + fill：GDI+ `ValueError`，`annotate_png` 无异常、只画线；
- 建议把点数检查挪进 `apply_pad`。

### 4.6 bounds_warn 重复（P2）

fill+stroke 同一 op 会出两条告警。本窗口实测：

```
['op[0] fill 超出画布：右 330px', 'op[0] stroke 超出画布：右 332px']
```

`tests/test_fill.py` 只断言 truthy，没查条数/数值。

### 4.7 radius 与 dpr / 小数（P2）

- `scale_ops` 只缩几何键，**radius 不缩放**：本窗口实测 `{x:10,y:10,w:100,h:100,radius:10} @dpr=2` → `x:20,w:200,radius:10`，视觉圆角半径减半；
- 像素路 `int(radius)` vs 矢量路 float：`radius=2.5` 时两路角落会有差异（子代理实测 6 像素）。

### 4.8 “两路一致”需要限定（P2）

- **规则层**一致：同一多边形在 nonzero 下两路填充区域应一致；
- **逐像素**不一致：实心 rect 120×80 两路差 9px（描边边），-90° 扇形差 190px（子代理实测）；
- 13 项测试只采中心/内点，没锁边缘；
- README/SKILL/CHANGELOG/设计文档的“两路一致/结果一致”应改成“填充区域规则一致；像素级边缘随后端”。

### 4.9 测试假绿与缺失（P2）

- `test_fill_concave_parity_nonzero_vs_evenodd` 的 6 点其实是两个同向三角形在顶点相接，nonzero/evenodd 同结果——**锁不住 Winding**；
- 真正判别形：五角星（点序 0,2,4,1,3），中心 winding=2；
- 缺：curve 填充面积（polyline 已有）、`radius=20` 圆角外点、降级管线 fill、扇形半径/闭合弦边缘采样。

### 4.10 文档漂移（P2）

- 设计文档 §4 标题仍写“10 项”，实际 13；§7 出现两次（“顺带记录”和“审查修正”）；
- MCP description 只写“line/text 给 fill 报错”，漏 arrow/step/number/像素 ops；
- README 的 13 项清单漏了 alpha 三条（8 位描边拒绝/透明底/alpha=00）。

### 4.11 MCP `ops` 是 string（P2）

- `ashot_annotate` 的 `ops` 在 schema 里是 **string**；
- 长 ops 在宿主/参数层可能被截断（设计文档记 v0.7.3 实测 >1KB 报 `JSONDecodeError`；直连 stdio 3669 字节可通，子代理实测）；
- 服务端 `json.loads` 失败没有“疑似截断（len=N）”的可操作报错；
- 建议 schema 改 array（handler 已兼容 list），并给带字节数的错误。

### 4.12 绕过 `apply_pad` 的 compile_ops（P2）

- `text + fill` 直接 `compile_ops` **静默丢弃 fill**（本窗口实测只出 `['text']`）；
- `line + fill` 直接 compile 报“fill 至少需要 3 个点”，不是“不支持”；
- `mosaic + fill` 原样进 `pixel_ops`；
- fill 的 kind 校验只有 `apply_pad` 一道门；建议 compile 也校验或统一入口。

## 5. 图层设计

### 5.1 轻图层 MVP（推荐先做）

```json
"layers": [
  {"id": "bg",  "name": "背景", "z": 0,  "visible": true},
  {"id": "fg",  "name": "前景", "z": 10, "visible": false}
],
"ops": [
  {"kind": "rect", "layer": "bg", "fill": "#87CEEB", "...": "..."}
]
```

- 按 `layer.z` 稳定排序，组内保持原顺序；
- `visible=false` 整层跳过；
- **保留原数组下标 `i`**（bounds_warn 指对 op）；
- `step`/`number` 仍按**原数组顺序**先编号，避免步骤号跳变；
- 像素 ops 一期明确：拒绝 `layer`，或文档写死“恒最上层”；不能收字段却排不了序；
- 降级路按同一排序执行（先修 §4.2）。

### 5.2 真图层（二期）

- 每层画到独立 RGBA canvas，再按 `opacity`/blend 合成；
- 能修“半透明重叠暗缝”“像素 ops 恒最后”“组透明度”；
- 代价：内存 ×层数、GDI+ 多次启动、混合模式要自己实现；
- per-op alpha 不能冒充组透明度（两个 50% 重叠变 75%，白底单区 127 / 重叠 63 已证）。

## 6. 实施顺序

1. **P1 fill-only / preview**：`stroke:false`（或 `stroke_width:0` 语义），preview 按固定底色合成并在收据写 `preview_alpha_lost`/背景色。
2. **P1 多子路径 / holes / chord**：`polyline/curve` 加 `holes`；arc 加 `chord`；用五角星/甜甜圈/人脸做真机。
3. **P1 两后端层序统一**：降级路按“形状段→像素 op→形状段”执行，或把规则标成 GDI+ 专属。
4. **P2 轻图层**：`layer:int` + `layers` 元数据；保留 i/step 约束。
5. **P2 组透明度/混合**：逐层离屏合成，单独版本。
6. **P2 收尾**：像素抗锯齿、radius 随 dpr、点数校验前移、bounds 按 op 合并、文档 10→13/§7 改名、MCP ops array。
